Critical architectural conclusion for the coding agent
- The source repo is not a simple one-to-one copy target.
- Source minigames are tied to a broader app shell with XState, auth context, farm state, reward flows, and iframe portal launching.
- The target repo uses a lighter architecture with local React state, nanostores, popup helpers, and portal/session helpers.
- Therefore, implementation should not blindly copy source files.
- Instead, port concepts and behaviors into target-native abstractions.

Important uncertainty the coding agent must respect
- The following minigame ids are known in source research and/or target checklist:
  - `goblin-invaders`
  - `tetris`
  - `barley-breaker`
  - `pac-man`
  - `frogger`
- However, this research did not confirm local source gameplay files for those five in the inspected `Sunflower-Land` branch.
- Treat them as unresolved with respect to source implementation location.
- Do not fabricate direct file mappings such as `mini-games/tetris/TetrisGame.tsx` unless the agent independently verifies them.
- If those games are externally hosted portal games rather than in-repo implementations, prefer portal/session integration over fake local copies.

Required agent behavior
- Use the checklist as the source of truth for progress tracking.
- Preserve completed implementations.
- Refactor only when it reduces duplication and does not destabilize existing games.
- Leave notes/TODOs where source parity is uncertain.
- If implementing unresolved games locally, do so in a clean target-native structure rather than pretending they came from verified source files.
- If implementing unresolved games as hosted/portal games, build the minimal target-side infrastructure needed to support that cleanly.

Recommended migration strategy
1. Stabilize and normalize the existing arcade game architecture.
2. Extract shared arcade patterns used by the five completed card games.
3. Introduce a scalable game registration mechanism so the remaining checklist items can be added with minimal `if`-chain growth.
4. Add a status/metadata system that reflects checklist progress in code.
5. Implement unresolved games one by one, choosing either:
   - local target-native implementation, or
   - portal-hosted integration,
   based on what the agent can verify from source.
6. Update hub UX so completed items become playable and unresolved items remain clearly marked.

Concrete coding tasks
Task 1: Replace hard-coded arcade branching with a registry
- Current file: `src/features/arcade/NightshadeArcadeApp.tsx`
- Problem:
  - The component currently uses many explicit `if (activePlayableGame === ...)` branches.
  - This will become harder to maintain as the checklist grows.
- Goal:
  - Introduce a registry/config-based mapping from game id to playable component or launch behavior.
- Suggested outcome:
  - A central game registry module under `src/features/arcade/` or `src/features/arcade/games/`.
  - The registry should support:
    - local component-backed games,
    - future portal-backed games,
    - metadata for status, labels, and reward behavior.

Task 2: Keep `hubConfig.ts` aligned with the checklist
- Current file: `src/features/arcade/data/hubConfig.ts`
- Goal:
  - Ensure the checklist and hub metadata stay synchronized.
  - If useful, split metadata into reusable types or registries.
- Requirement:
  - Preserve current completed/incomplete status unless implementation changes justify updating it.

Task 3: Extract reusable game shell patterns
- Existing repeated concerns across completed games:
  - back button behavior
  - token reward callback behavior
  - start/restart UX
  - status text layout
  - consistent page shell styling
- Goal:
  - Create shared helper components/hooks/utilities where appropriate.
- Warning:
  - Do not over-abstract unique game logic.
  - Share shells, controls, and reward plumbing before sharing game rules.

Task 4: Decide and implement support path for unresolved games
Checklist items:

For each unresolved item, the coding agent must determine one of two paths:
Path A: local implementation in target
- Create target-local implementation under `src/features/arcade/games/<game>/`
- Add any needed shared helpers
- Register the game in the arcade registry
- Update hub status to playable only when complete

Path B: portal-hosted integration in target
- Reuse or extend target portal/session utilities:
  - `src/lib/portal/sessionProvider.tsx`
  - `src/lib/portal/processAction.ts`
  - `src/lib/portal/closePortal.ts`
- Introduce a clean target-side launcher flow for hosted games
- Ensure closing, reward synchronization, and popup interactions are coherent
- Mark the game playable only after the integration path is real and testable

Task 5: Introduce an explicit implementation-status surface for agent work
- Add a developer-facing progress structure in code or docs so future agent passes can quickly see:
  - complete games
  - in-progress games
  - unresolved-source games
  - portal-backed vs local-backed games
- This can be done in code comments, a registry field, or a supporting doc.

Task 6: Preserve and document uncertainty
